# Ключові питання уроку m4-l03 "property замість геттерів і сеттерів; __slots__"

Урок готовий, коли на кожне питання є відповідь з кодом і виводом.

- [x] Чому в Python не пишуть `get_x`/`set_x`: починають з публічного атрибута, а коли потрібна логіка, перетворюють на `property` без зміни інтерфейсу (uniform access). Порівняти з TS `get x()`/`set x()`.
- [x] `@property`, `@x.setter`, `@x.deleter`: синтаксис, read-only властивість без setter (`AttributeError: property ... has no setter`), валідація в setter, обчислювані властивості (без кешу).
- [x] Коли property не варто: дорогі обчислення (користувач очікує дешевого доступу), побічні ефекти, I/O. `functools.cached_property` для обчислення один раз і його пастка з змінюваним станом.
- [x] Під капотом: property це дескриптор; протокол дескрипторів `__get__`, `__set__`, `__set_name__` на прикладі власного `Validated`-дескриптора для полів з перевіркою типу. Чому дескриптор живе на класі, а не на екземплярі. Згадати, що `@classmethod`, `@staticmethod`, функції це теж дескриптори.
- [x] `__slots__`: що робить (немає `__dict__`, фіксований набір атрибутів, менше пам'яті, захист від одруків `obj.nmae = ...`), виміряти пам'ять через `sys.getsizeof` або `tracemalloc` на 100k об'єктів, обмеження (наслідування, `__weakref__`, динамічні атрибути). `dataclass(slots=True)` як зручний шлях (посилання на m2-l05).
- [x] Валідація через property проти через Pydantic (m2-l09) проти через `__post_init__` (m2-l05): де яка доречна.
- [x] Для капстоуну: `GenerationJob.status` як property з перевіркою допустимих переходів (queued → running → done/failed), `duration` як обчислювана властивість, `__slots__` для об'єктів, яких буде багато (елементи дерева).
- [x] Які JS-звички тут шкодять: `Object.defineProperty`, геттери з побічними ефектами, `private` поле + геттер як норма, очікування, що властивість можна додати на екземпляр (property лише на класі).
