# Нотатки до m5-l08 "GIL, threading, multiprocessing, concurrent.futures: що куди"

## Що запускалось

Усе через `.venv/bin/python` (CPython 3.12.12, macOS, Apple M1 Pro, 10 ядер, start method `spawn`). Тимчасові файли лежали в `<scratchpad>/m5-l08/` і видалені після перевірки.

- Кожен блок `python` у `lesson.md`, за яким іде блок `text` (26 блоків, з них 3 `live`), витягнутий скриптом і запущений окремим файлом через `/usr/bin/time -p .venv/bin/python exNN.py`; stdout порівняно з уроком. Збігаються дослівно всі, крім очікуваних розбіжностей: виміряний час (у межах кількох сотих), pid процесів, адреси `<lambda> at 0x...`, конкретні числа в демо гонитви. Вивід у прикладі "heartbeat" оновлено на значення з контрольного запуску.
- Демонстрація гонитви: `counts[k] = counts.get(k, 0) + 1` з 4 потоків по 200 000. З дефолтним switch interval результат неправильний у більшості, але не в усіх запусках (у тексті це показано і названо); з `sys.setswitchinterval(1e-6)` неправильний у кожному з 15+ запусків (~330 000 замість 800 000). Класичний `counter += 1` на 3.12 не рвався ні разу навіть з `1e-6`, це пояснено в callout через точки перевірки eval breaker і `dis`.
- Приклад з deadlock детермінований: daemon-потоки + `join(timeout=1)`, 3 запуски, вивід `still alive: [True, True]` щоразу.
- Приклад без `if __name__ == "__main__"` прогнаний з ручним таймаутом; урок показує скорочений вивід (stdout і stderr разом, ~150 рядків у повному вигляді), про скорочення сказано в тексті.
- `tasks.yaml` читався через pyyaml. Для кожного `type: code` запущено `solution + harness` (stdout збігається з `expected` після нормалізації) і `starter + harness` (не проходить). Для локальних t3, t4, t5 команда `verify` виконана в тимчасовому "корені курсу" (`root/practice/m5-l08/` + симлінк `root/.venv`) двічі: з кодом стартера (падає) і з рішенням (друкує `OK`). Для t3 додатково перевірено, що рішення з реалізованим `hammer`, але без lock-а в `record`, падає з `lost updates`.
- Перевірено, що кожен id з `tasks.yaml` вставлений у `lesson.md` рівно один раз і зайвих вставок немає.

Живі блоки (`sys.getswitchinterval`, ручний `Future`, `pickle` з різними об'єктами) не потребують потоків; у Pyodide вони не запускались, лише в CPython. Адреса `0x...` у прикладі з pickle в браузері буде іншою.

## Рішення

- 8 розділів теорії (включно з "Для капстоуну") + 3 закривальні, близько 36 абзаців теорії і 9 callout-ів. Багато прикладів (26 запусків), бо майже кожне твердження тут про поведінку, яку треба показати виміром; поділу не пропоную.
- Завдання: 5 code (t1, t2 browser як чисті функції; t3, t4, t5 `runtime: local`), 4 quiz, 1 project (капстоун). Локальні завдання живуть у `practice/m5-l08/` у корені курсу; `verify` запускається з кореня курсу без `cd`: `PYTHONPATH=practice/m5-l08 .venv/bin/python -c "..."` (конвенція `docs/lesson-spec.md`). Редакторська правка: після заміни `cd practice/m5-l08 && ../../.venv/bin/python` на `PYTHONPATH` усі три `verify` перепрогнано в scratch-копії кореня курсу: стартер падає, рішення друкує `OK`; для t5 дочірні процеси `spawn` успадковують `PYTHONPATH` і імпортують `build_pages`. Для local code-завдань також дані `harness`/`expected`, що дублюють `verify`, для єдиного формату.
- t3 у `verify` ставить `sys.setswitchinterval(1e-6)` і повторює прогін тричі, щоб версія без lock-а гарантовано падала. t4 має перевірку часу в `assert` (< 0.45 с при сумі затримок 0.75 с), не в `expected`-виводі харнесу, а там лише булеве значення.
- t5 перевіряє, що рендер справді йде в процесах, через `render_pid` у стартері: файли не повинні містити pid батька. Вимога guard-а переформульована як умова для демо-запуску, бо `verify` імпортує модуль.
- free-threaded збірка дана одним реченням (3.13 експериментальна, 3.14 офіційно підтримувана, але не за замовчуванням).
- `multiprocessing.Process`, `Pool`, `Manager`, `shared_memory` не розбирались окремо: урок веде через `concurrent.futures` як рекомендований шлях; `shared_memory` лише згадано як аналог `SharedArrayBuffer`. `fork`/`forkserver` названі, але не показані (на macOS безпечний лише `spawn`).
- `run_coroutine_threadsafe` у m5-l05 не розібраний (там лише `to_thread` і `run_in_executor`), тож тут він пояснений повністю разом із `call_soon_threadsafe`.
